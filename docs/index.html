01

Frame rate,
unlocked.

The game loop is no longer welded to 60fps. AtomHax lifts the rAF cap and keeps the present queue short enough that the compositor always shows the newest frame.

0fps ceiling

Vanilla HaxBall throttles requestAnimationFrame to your monitor's refresh. AtomHax patches the gameframe's rAF directly — inside the iframe realm, where the game actually schedules — and keeps vsync on so the present queue never backs up.

rAF unlocked per-iframe — the patch overrides the realm the game loop lives in
Game-loop tick multiplier: more simulation steps per compositor frame
Canvas rendering untouched — stadium and player lines identical to vanilla

02

Scripting that
runs in-process.

Tampermonkey-style scripts load from disk, inject into the right JS realm automatically, and get a bridge straight into the running engine.

my-first-script.js — injected into gameframe 
1// ==UserScript==2// @name       Ball proximity alert3// @noframes   true4// ==/UserScript==56const g = window.parent.g;7const beep = new Audio("ping.mp3");89setInterval(() => {10  const s = g.snap();11  if (!s.ok || !s.me || !s.ball) return;12  const d = Math.hypot(s.ball.x - s.me.x, s.ball.y - s.me.y);13  if (d < 45) beep.play();14}, 100);

Right realm, first load

Scripts marked @noframes run in the top-level page; everything else injects straight into the gameframe's JS context via WebFrameMain.executeJavaScript on did-frame-finish-load — no cross-origin workarounds, no silent no-ops.

Engine bridge

The shipped engine installs window.parent.g: snap() for positions, in()/out() for input masks, opGet()/opSet() for power. Your script polls real match state — ball, players, field, frame number.

Managed in the client

Import, enable/disable, delete, and reload from the sidebar. Scripts persist in scripts.json; toggling one only requires the built-in gameframe reload — no app restart.
