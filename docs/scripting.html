Scripts, explained.

AtomHax loads plain JavaScript files from disk and injects them into the running HaxBall page at the right moment. Choose the page they run in, then use the small bridge inside the client to read live match state and send input.

Scripts run in your own client, in your own session, with your own privileges. They are regular page JavaScript — no sandbox, no review. Don't run scripts you haven't read.

Script anatomy

A script is any .js file with an optional userscript-style metadata header. The header is parsed with simple line comments — nothing else about it is special.

script header
// ==UserScript==
// @name       Ball proximity alert   // shown in the scripts UI
// @version    1.0.0
// @noframes   true                    // controls where the script runs — see below
// ==/UserScript==

// everything after the header is a normal IIFE or top-level code
(function () {
  'use strict';
  // ...
})();
FieldEffect
@nameDisplay name in the scripts panel. string
@versionInformational. string
@noframes When set to true, the script runs in the top-level page (the Electron renderer document). When absent or false, it runs inside the gameframe, in HaxBall's own JS window.

Injection contexts

Each script runs in exactly one of two JS windows. Pick based on what your script touches:

Gameframe (default)Top-level (@noframes true)
Where html5.haxball.com iframe document The Electron window document
Can reach Game DOM (canvas, chat, room view), engine objects Client UI, other frames via document.querySelector('iframe.gameframe')
Engine bridge window.parent.g window.g (same object)
Injected when did-frame-finish-load on the gameframe did-frame-finish-load on the top page
Good for Gameplay hooks, HUD overlays, input control DOM tweaks around the game, scripts that manage the gameframe

In either window, write code that works in both if it helps: check window.g first, fall back to window.parent.g. The engine bridge is installed by the patched engine that ships with the client — it is present from the moment the gameframe loads.

Engine bridge · window.parent.g

The bridge is a single object installed at gameframe load. It is deliberately tiny and stable — the function names are the API. Handle identity: the object exposes a bh marker you can check before use.

MemberSignatureWhat it does
bh 1—Presence marker. If window.parent.g?.bh is falsy, the bridge isn't there yet.
snap() → SnapResultOne-shot copy of live match state. Read-only, safe to poll.
in(mask: string) → 0 | 1Presses a virtual input (adds it to the engine's active-input set).
out(mask: string) → 0 | 1Releases a virtual input.
opSet(v: number) → numberSets power, clamped to 0–100. Returns the applied value.
_rmobjectInternal room-manager handle. Unstable — use snap() instead of reaching into it.

g.snap()

Returns a snapshot object. Every field except ok may be missing when there is no game running — check ok first, then null-check what you use.

FieldTypeMeaning
ok0 | 11 when a room with a running game was reachable.
pidnumberYour player id in the current room.
ball{x, y, vx, vy, r}Ball position, velocity, radius. Coordinates in stadium units.
me{x, y, r}Your user circle position and radius. Missing when spectating or not spawned.
playersnumberPlayer count in the room.
fieldW / fieldHnumberField bounding box, derived from the stadium discs. Defaults to 800×560 if the stadium shape can't be measured.
framenumberCurrent game frame counter.
tsnumberDate.now() when the snapshot was taken.
polling snapshot
const g = window.parent.g;

setInterval(() => {
  const s = g.snap();
  if (!s.ok || !s.me || !s.ball) return;   // no game, or spectating
  const dist = Math.hypot(s.ball.x - s.me.x, s.ball.y - s.me.y);
  // dist is in stadium units; player radius is usually 15, ball 10
}, 50);

g.in() / g.out()

These drive the engine's own input set — the same set your physical keys feed. A mask is one of the five action strings. in is "hold", out is "release". Returns 1 when applied, 0 when the room/input controller isn't available yet.

MaskMeaning
'Up' | 'Down' | 'Left' | 'Right'Movement directions.
'Kick'Kick / grab action.
tap pattern — press, hold, release
const g = window.parent.g;

function tap(mask, holdMs = 40) {
  if (!g) return;
  g.in(mask);
  setTimeout(() => g.out(mask), holdMs);
}

// hold Left for 120ms, then release
tap('Left', 120);
Don't leak masks. If your script holds a direction, release it when the game stops (room change, spectate) or the user circle will keep drifting after your script's window closes. Track what you pressed and call g.out() on cleanup.

g.opSet()

Power value, integer 0–100, clamped on set. Zero disables; the engine's stock default is 5.

power
g.opSet(25);      // returns 25
g.opSet(9001);   // clamped → returns 100

Storage

Scripts live in scripts.json inside the app's userData directory (%APPDATA%/atomhax/ on Windows). The format is a flat array — edit it while the client is closed if you want to bulk-import.

scripts.json
[
  {
    "id": "a1f0...",        // generated at import time
    "name": "Ball proximity alert",
    "content": "// ==UserScript== ...",   // full file contents, header included
    "enabled": true
  }
]

Only enabled scripts are injected, and they run on every gameframe load for the whole session — joining a room, changing rooms, opening a replay all re-inject. Scripts that touch global state should guard against double-run (see patterns).

Lifecycle & timing

  1. Injection point. Scripts are executed via WebFrameMain.executeJavaScript on did-frame-finish-load. For gameframe scripts that means the frame's DOM is parsed but the game script may still be initializing — attach with the same tolerance you'd use on the real site: poll or wait for elements rather than assuming they exist on line one.
  2. Re-render. HaxBall rebuilds parts of its DOM when you move between screens. Anything you appended to the game document can vanish. Re-check existence in your loop, or observe the document with a MutationObserver.
  3. Focus. The gameframe is focused while playing; keydown listeners attached from the top-level page won't see keystrokes destined for the game. Scripts that need keyboard input should run in the gameframe window (no @noframes) or attach listeners to gameframe.contentDocument.
  4. Reload semantics. Editing or toggling a script in the UI does not retro-inject — it applies on the next gameframe load. Use the client's reload gameframe action to re-run everything.
  5. Single-init guard. Injection happens per frame load; the top-level page can also trigger extra loads. Guard your script's global state: if (window.__myScriptLoaded) return;

Patterns

Works in both windows

works in both windows
function getBridge() {
  try { if (window.g && window.g.bh) return window.g; } catch (e) {}
  try { if (window.parent && window.parent.g && window.parent.g.bh)
        return window.parent.g; } catch (e) {}
  return null;
}

Don't hijack the game's keys while typing

Chat input steals focus when the user types. Guard your hotkey handler:

typing guard
function isTyping() {
  const el = document.activeElement;
  if (!el) return false;
  const tag = (el.tagName || '').toUpperCase();
  return tag === 'INPUT' || tag === 'TEXTAREA' || el.isContentEditable;
}

document.addEventListener('keydown', (e) => {
  if (isTyping()) return;
  // your hotkey logic
}, true);   // capture: beat the game's own handlers

Stable gameframe document reference

top-level scripts only
function getGameDoc() {
  const f = document.querySelector('iframe.gameframe');
  if (!f) return null;
  try { return f.contentDocument || null; } catch (e) { return null; }
}

Full example

A complete, minimal script: chase assist. It keeps the user circle moving toward the ball while a hotkey is held, and cleans up its input on room loss.

chase-assist.js
// ==UserScript==
// @name       Chase assist
// @version    1.0.0
// ==/UserScript==
(function () {
  'use strict';
  if (window.__chaseAssist) return;      // single-init guard
  window.__chaseAssist = true;

  const g = window.parent.g;
  if (!g || !g.bh) return;

  let held = false;
  const KEY = 'KeyT';

  function isTyping() {
    const el = document.activeElement;
    const tag = el ? (el.tagName || '').toUpperCase() : '';
    return tag === 'INPUT' || tag === 'TEXTAREA';
  }

  document.addEventListener('keydown', (e) => {
    if (e.code === KEY && !isTyping()) held = true;
  }, true);

  document.addEventListener('keyup', (e) => {
    if (e.code === KEY) {
      held = false;
      g.out('Left');
      g.out('Right');
    }
  }, true);

  setInterval(() => {
    const s = g.snap();
    if (!s.ok || !s.me || !s.ball || !held) {
      if (!s.ok) { g.out('Left'); g.out('Right'); }
      return;
    }
    const dx = s.ball.x - s.me.x;
    g.in(dx >= 0 ? 'Right' : 'Left');
    g.out(dx >= 0 ? 'Left' : 'Right');
  }, 16);
})();

Import it from the sidebar (Scripts → import), enable it, reload the gameframe. The loader parses the header, runs the IIFE inside the gameframe, and the guard makes repeat injections harmless.
